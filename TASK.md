# 03. Тестовое задание — Python-разработчик (LLM/ИИ-агенты), Junior+

## Контекст для кандидата

Мы ищем Python-разработчика, который будет строить LLM-сервисы и ИИ-агентов для внутренних
подразделений. Первый проект — финансовая служба: агент, который отвечает на вопросы по
учётным данным (1С) и по регламентным документам, с проверяемыми расчётами и ссылками
на источники.

Тестовое задание — модель первого рабочего спринта, сокращённая до 4–6 часов. Полнота
продукта не требуется: важнее архитектурные решения, корректность и объяснимость.

## Ограничение по времени

База рассчитана на **4–6 часов** — это основной таймер. Бонусы из раздела «Дополнительно» —
сверху, ещё 1–2 часа, и они не обязательны для положительной оценки.

Зачётный минимум (без него решение не разбираем):

- 2–3 инструмента по данным с расчётом кодом;
- один RAG-ответ с дословной цитатой из `docs/`;
- JSON-ответ по схеме ниже и честный отказ, когда данных нет;
- запуск одной командой;
- 2–3 автотеста.

Время вышло — доведите минимум и напишите в README, что не успели: это не минус.

## Объём работы (важно прочитать)

Это скоуп MVP на 4–6 часов, а не полный продакшен-сервис. **Намеренно вне объёма:**

- персистентность приложения — история запросов, сессии, очередь (in-memory достаточно,
  чтобы проверить, что флоу работает); SQLite/Postgres как способ читать `data/` — допустим;
- авторизация и разграничение прав пользователей;
- очереди, фоновые задачи, горизонтальное масштабирование;
- self-hosted GPU-инференс (LLM и эмбеддинги).

Но решение должно быть **продакшен-образным по скелету**: интерфейсы вместо хардкода,
конфиг через env, логирование/трассировка, аккуратная обработка ошибок — чтобы
продакшен-вещи (персистентность, кэш, очередь, auth) встраивались без переписывания.
Где вы сознательно упростили для MVP и что бы сделали иначе для прода — опишите в README.

**Целевой уровень — аккуратный MVP с продакшен-образным скелетом.** Делать «по максимуму»
(self-hosted эмбеддинги на GPU, RRF и реранкер на два документа, LLM-судья на каждый
прод-запрос) НЕ нужно: база знаний — два markdown-документа, для такого объёма это
оверанжиниринг. Каждая добавленная сложность должна быть обоснована данными и профилем
нагрузки, а не принципом «чтобы наверняка» — обоснованный отказ от лишнего идёт в плюс.
Локальные эмбеддинги на CPU — нормально, GPU под десятки чанков избыточен.

База важнее бонусов: если время заканчивается, доводите минимум, а не добирайте бонусы.

## Нефункциональные требования (NFR)

Профиль сервиса: внутренний помощник финслужбы — десятки пользователей, пик ~2–5 запросов/мин,
до 10–20 одновременных пользователей. Горизонт — год без перепроектирования. Это НЕ
RPS-челлендж: важнее стабильность и понятный бюджет, чем миллисекунды.

Латентность (end-to-end, измеряется скриптом на том интерфейсе, который вы сделали —
HTTP POST /ask или CLI):

| Тип вопроса | Ориентир, не более | Эталонный вопрос |
|---|---:|---|
| Простой расчётный (1 инструмент) | 10 с | «Сколько дебиторской задолженности у контрагента „Ромашка"?» |
| RAG-вопрос с цитатами | 12 с | «Что делать при просрочке дебиторки 45 дней?» |
| Многошаговый (несколько инструментов) | 25 с | «Топ-5 должников по сумме просрочки» |

Ориентиры — не пропускной критерий: если не уложились, покажите, что измерили и знаете,
где узкое место. Доминанта бюджета — вызовы LLM API, а не ваш код.

Отказоустойчивость:

- таймаут на каждый внешний вызов (LLM; векторное хранилище — если оно внешнее);
- 1–2 ретрая на 429/5xx с задержкой — экспоненциальная или фиксированная, на ваш выбор;
  важно, что попытки ограничены и нет шквала повторов;
- «вечных» запросов нет; при сбое — честный `status`/ошибка в JSON, а не выдуманный ответ.

Компьют:

- эмбеддинги: API или локальная модель на CPU (sentence-transformers) — данных мало, GPU не нужен;
- self-hosted GPU-инференс — вне объёма (см. «Объём работы»);
- модель LLM — см. «Стек».

Стоимость — считаем, а не угадываем:

- токены и число витков на запрос (см. бонус 3 «Трейсинг»);
- лимит витков и бюджета токенов — чтобы один вопрос не сжёг бюджет;
- дешёвая модель для рутины — по желанию.

Как измерять: 3 вопроса — по одному на каждый тип из таблицы выше; 10–15 прогонов на вопрос;
скрипт на curl/httpx + time (или pytest-бенчмарк). В README — таблица: вопрос, медиана, худший
результат, токены, стоимость. p95 на таком числе прогонов не считается — приводим медиану
и максимум.

## Данные (выдаём, ничего выгружать не нужно)

- `data/` — пример выгрузки из 1С за 01.01.2026 – 31.07.2026 (CSV):
  - `counterparties.csv` — контрагенты;
  - `invoices_issued.csv` — счета покупателям (реализация);
  - `invoices_received.csv` — счета от поставщиков;
  - `payments.csv` — платежи;
  - `account_balances.csv` — остатки/обороты по счетам учёта;
  - `receivables.csv` — развёрнутая дебиторка (авторитетный источник по просрочке:
    поля `status` + `overdue_days`).
- `docs/` — регламенты финслужбы (markdown), источник для RAG:
  - `uchet_politika.md` — фрагмент учётной политики;
  - `reglament_debitor.md` — регламент работы с дебиторской задолженностью.

## Обязательная часть

Создать Python-приложение, которое:

1. принимает вопрос через CLI или HTTP (FastAPI: POST /ask);
2. отвечает на вопросы по финансовым данным из `data/`. Примеры:
   - «Сколько дебиторской задолженности у контрагента „Ромашка"?»
   - «Какая сумма просроченной дебиторки на 31.07.2026?»
   - «Топ-5 должников по сумме просрочки»
   - «Обороты по счёту 62 за Q2 2026 (Дт, выставлено)»
   - «Сколько мы должны поставщикам по счетам со сроком оплаты в августе 2026?»

   Это примеры, а не закрытый список: на разборе мы зададим 1–2 вопроса по тем же данным
   вне примеров — решение должно отвечать на них, а не только на заученные формулировки.
3. выполняет расчёты **только кодом через инструменты** (Python/SQL), а не «в голове» у LLM;
4. отвечает по регламентам из `docs/` с цитатами (RAG):
   - «Что делать при просрочке дебиторки 45 дней?»
   - «Как формируется резерв по сомнительным долгам?»
5. возвращает структурированный JSON-ответ: поля `answer`, `status`, `calculations`, `sources`
   и `warnings` обязательны, вложенные — на ваше усмотрение;
6. при отсутствии данных честно говорит об этом, не выдумывает;
7. содержит 2–3 автотеста (pytest): расчёт инструмента, честный отказ при отсутствии данных,
   наличие цитаты в RAG-ответе;
8. запускается одной командой (README: как);
9. не содержит секретов (ключ только через env/.env; `.env` — в `.gitignore`, в репозиторий
   только `.env.example`);
10. валидирует входные данные (схема запроса, лимит длины) и работает с данными только на чтение;
11. обрабатывает ошибки инструментов и внешних вызовов (таймаут, ретрай) — не падает и не
    выдумывает ответ.

### Пример ответа

```json
{
  "answer": "ООО Ромашка должно компании 2 600 080,15 рублей",
  "status": "ok",
  "calculations": [
    {
      "operation": "sum",
      "expression": "1512769.77 + 1087310.38",
      "result": 2600080.15,
      "currency": "RUB"
    }
  ],
  "sources": [
    {
      "type": "data",
      "file": "receivables.csv",
      "record_ids": ["СБ-00026", "СБ-00010"]
    }
  ],
  "warnings": []
}
```

Для табличных данных ссылайтесь на **устойчивые идентификаторы записей** (номер счёта
СБ-XXXXX/ВХ-XXXXX, номер платежа ПЛ-XXXXX, ИНН контрагента), а не на номера строк —
строки меняются при сортировке.

Для RAG-ответа источник — файл, раздел и дословная цитата, например:
`{"type": "document", "file": "docs/reglament_debitor.md", "section": "Стадия 3", "quote": "При просрочке от 45 дней …"}`.

## Стек

- Python 3.11+; любой агентный фреймворк (PydanticAI, LangGraph, OpenAI Agents SDK, smolagents)
  **или** написанный руками tools-loop — допустимо и ценится понимание;
- можно использовать **детерминированный workflow вместо агентного цикла**: для нескольких
  типов запросов это часто правильнее. Выбор обоснуйте надёжностью и требованиями задачи,
  а не модой. Классификатор намерения + типизированные инструменты + детерминированный
  маршрут — это не недостаток, а признак зрелости;
- LLM: любой OpenAI-совместимый API на вашем ключе, либо локальная модель (Ollama) —
  ключи от нас не выдаются;
- векторное хранилище: любое (pgvector, Qdrant, FAISS, Chroma) или in-memory с обоснованием;
- работа с данными: pandas **или** SQL (SQLite/Postgres) — на ваш выбор, обоснуйте; у нас
  в проде PostgreSQL, так что SQL приветствуется;
- зависимости и запуск: requirements.txt / uv / Docker, git-репозиторий.

## Дополнительно (по желанию)

База важнее бонусов: если время заканчивается, доводите минимум, а не добирайте бонусы.
Бонусы копятся, если остаётся время; учитываются они отдельной строкой и базу не заменяют.

1. **MCP-сервер**: один-два инструмента для доступа к данным через MCP (например,
   `debt_snapshot`), агент подключается как MCP-клиент. Кратко опишите протокол: JSON-RPC,
   initialize → tools/list → tools/call, stdio vs HTTP, чем tools/call отличается от
   обычного function calling.
2. **Eval-прогон**: 10–15 кейсов (вопрос + ожидаемый факт/число), включая 3–5 негативных
   (вопроса нет в данных — агент обязан честно сказать; «подвох» — посчитать по данным,
   а не процитировать регламент). Отчёт: точность, faithfulness, стоимость в токенах,
   число витков на вопрос. Ожидаемые факты и числа считаете сами по `data/` — это часть
   бонуса. LLM-судья внутри eval-прогона допустим, в рантайме на каждый запрос — нет.
3. **Трейсинг**: логировать трассу каждого ответа — витки, вызовы инструментов, токены
   (файл JSON или stdout-лог).
4. **Human approval для изменяющей операции**: инструмент подготовки платежа-черновика
   (`draft_payment`, dryRun, валидация обязательных реквизитов, ответ — ссылка на черновик,
   НЕ проведение). Покажите, как сервер не даёт LLM выдумывать реквизиты: JSON-схема/шаблон
   документа на стороне сервера, а не «напиши что хочешь». Фактическая запись или проведение
   платежа — не бонус, а стоп-фактор.
**Свободная строка README, баллов не даёт** (материал для разбора на собеседовании): 3–5 вещей,
которые вы добавили бы перед продакшеном (например: персистентность и аудит, auth/RBAC, очередь,
семантический кэш, observability и evals в CI), и как они легли бы на вашу архитектуру.
Это «план продакшена на бумаге» — реализовывать не нужно.

**Отдельно от списка выше — бонус за предметное понимание** (+2, по желанию): опишите
2–3 рутинные задачи финслужбы,
которые видны в данных (работа с дебиторкой, сверка с поставщиками, контроль расчётного
счёта и т.п.), и как их автоматизировать агентом; что из этого реально внедрить за первый
месяц на нашей инфраструктуре (Python, LLM, 1С — стек за вами). Хороший ответ привязывает
идеи к конкретным данным/отчётам, а не пересказывает общие места про «ИИ в финансах».

## Критерии оценки

База (100%). Проходной балл базы — **70 из 100**, с меньшим на разбор не приглашаем.

NFR (таймауты, ретраи, лимиты, замер латентности) — не отдельная строка баллов, а часть
«Архитектуры» и «Работы инструментов»; промах по ориентирам латентности баллов не снимает.

| Что | Вес |
|---|---:|
| Корректность расчётов и отказ от выдумывания | 25% |
| Работа инструментов и управление ошибками | 15% |
| RAG, цитаты и groundedness | 20% |
| Архитектура и безопасность (read-only, валидация входа, секреты, лимиты витков) | 20% |
| Качество Python-кода и тесты | 15% |
| README и воспроизводимость | 5% |

Бонусы (сверх 100%, считаются отдельной строкой и базу не заменяют; при равенстве базы
решает бонус):

- MCP-сервер: до +5;
- evals: до +5;
- трейсинг: до +3;
- human approval: до +5;
- разбор бизнес-сценариев: до +2.

## Стоп-факторы (решение отклоняется независимо от оценки)

- секреты/ключи в репозитории (кроме `.env.example` без значений);
- финансовые расчёты, сделанные LLM, а не кодом;
- выдуманные источники/цитаты;
- произвольное выполнение SQL: запрос, собранный LLM из свободного текста и исполненный
  без ограничений. Допустимо — фиксированный набор параметризованных запросов-инструментов
  либо read-only соединение с allowlist таблиц/полей и обязательным LIMIT; при работе через
  pandas правило про произвольные запросы к данным действует так же;
- отсутствие проверки входных данных: нет схемы или лимита длины вопроса и отказа на пустой
  запрос;
- изменение данных (или `data/`) без подтверждения — актуально, если делали бонус с `draft_payment`.

«Проект не запускается» становится стоп-фактором только после того, как мы попросили показать
запуск и дали один шанс исправить локально.

## Правила

- Срок: база 4–6 часов, бонусы — сверху 1–2 часа и необязательны. Результат — ссылка
  на git-репозиторий.
- В README: как запустить, обоснование стека (агент vs детерминированный workflow), таблица
  замеров (вопрос, медиана, худший результат, токены, стоимость), что упрощено для MVP
  и что бы вы сделали для продакшена.
- Свои API-ключи никому не передавайте. Данные из задания нельзя выгружать целиком в публичные
  сервисы, датасеты и песочницы и нельзя обучать на них модели; передача фрагментов текста
  внутри API-запроса к LLM — обычная работа, а не выгрузка.
- Финал — разбор решения по коду на собеседовании: будьте готовы объяснить, почему выбрали
  агентный цикл или детерминированный workflow, и что бы улучшили. Ответ о решении дадим
  в течение 5 рабочих дней после сдачи.
- После найма эти же темы (MCP-мост к 1С, evals, трейсинг, human-in-the-loop) становятся
  рабочими задачами — дорастим на реальном проекте.
