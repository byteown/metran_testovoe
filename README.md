# fin-agent

LLM-агент финансовой службы: отвечает на вопросы по учётным данным из 1С (`data/*.csv`) и по внутренним регламентам
(`docs/*.md`), возвращает структурированный JSON с расчётами и ссылками на источники.

Все числа считаются кодом через типизированные инструменты. Языковая модель выбирает инструмент и формулирует фразу —
она не участвует в арифметике и не может изменить ни одно значение в полях `calculations` и `sources`.

## Быстрый старт

Нужны [uv](https://docs.astral.sh/uv/) и [Ollama](https://ollama.com/).

```bash
ollama pull qwen2.5:7b-instruct
```

```bash
cp .env.example .env
```

```bash
uv run fin-agent "Сколько дебиторской задолженности у контрагента Ромашка?"
```

`uv` сам скачает Python 3.11, создаст окружение и поставит зависимости из `uv.lock`. Первый запуск дольше: скачивается
модель эмбеддингов (~0,5 ГБ, один раз).

### HTTP

```bash
uv run uvicorn fin_agent.main:app
```

```bash
curl -X POST http://localhost:8000/ask -H "Content-Type: application/json" -d "{\"question\": \"Топ-5 должников по сумме просрочки\"}"
```

## Архитектура

```
вопрос
  ↓
AskRequest          валидация: непустой, ≤ 500 символов
  ↓
agent/loop.py       цикл function calling, ≤ 4 витков, бюджет токенов
  ├─ agent/llm.py   HTTP к Ollama: таймауты, ретраи, учёт токенов
  └─ agent/registry.py
       ├─ tools/finance.py  →  storage/db.py   SQLite в памяти, read-only
       └─ tools/rag.py      →  rag/index.py    эмбеддинги на CPU + косинус
  ↓
Answer              answer / status / calculations / sources / warnings
```

Ключевое свойство: `calculations` и `sources` собираются в `loop.py` **напрямую из результатов инструментов**, минуя
модель. Даже если модель напишет в тексте неверное число, в структурированных полях останется то, что посчитал код — на
это есть тест (`test_numbers_come_from_tool_not_from_model`).

### Агентный цикл, а не детерминированный маршрут

ТЗ разрешает и то, и другое. Выбран цикл function calling с жёсткими рамками, потому что на разборе обещаны вопросы
**вне списка примеров**: классификатор намерения на шесть фиксированных сценариев на них ломается, а цикл с
типизированными инструментами покрывает окрестность формулировок.

При этом надёжность обеспечивает не маршрут, а инструменты: модель не порождает SQL, она заполняет аргументы, описанные
pydantic-моделями. Свобода выбора у неё есть, свободы вычислений — нет.

Цикл рукописный (~90 строк), без агентного фреймворка: на шесть инструментов и два домена фреймворк добавил бы
зависимость и слой абстракции там, где логика видна целиком.

### SQLite вместо pandas

Данные читаются из CSV в SQLite в памяти при старте. Причины:

- в проде заказчика PostgreSQL — запросы переносятся почти без правок, код на pandas пришлось бы переписывать;
- режим только чтения включается одной строкой (`PRAGMA query_only = ON`) и проверяем тестом, а «pandas только на
  чтение» — обещание, а не механизм;
- всех данных 130 строк: загрузка занимает миллисекунды, файла на диске не возникает, между запусками не остаётся
  состояния.

Индексы намеренно не создаются: на 130 строках они бесполезны.

### RAG без векторной базы

Два markdown-документа, ~7,5 тыс. символов, **18 разделов**. Индекс — матрица 18×384 в numpy, поиск — одно матричное
умножение, **14 мс**. Qdrant или FAISS здесь были бы мебелью; порог оправданности векторной БД начинается на несколько
тысяч документов.

Эмбеддинги — `paraphrase-multilingual-MiniLM-L12-v2` на CPU. Видеопамять целиком отдана языковой модели, от которой
зависит латентность.

Кеш эмбеддингов не делается сознательно: модель всё равно держится в памяти, потому что вопрос пользователя нужно
кодировать в момент запроса, а кодирование 18 чанков при уже загруженной модели занимает доли секунды. Кеш экономил бы
их ценой файла, инвалидации и кода.

**Чанкинг — по заголовкам разделов**, не окнами фиксированной длины: документы уже структурированы автором, а поле
`section` в источнике всё равно требуется форматом ответа.

### Порог релевантности подобран по замерам

| Запрос                                            | Максимальная близость |
|---------------------------------------------------|----------------------:|
| «Как формируется резерв по сомнительным долгам?»  |                 0,832 |
| «Что делать при просрочке 45 дней?»               |                 0,639 |
| «Сколько дебиторки у Ромашки?» (вопрос по данным) |                 0,559 |
| «Какая погода в Москве?»                          |             **0,090** |

Порог `RAG_MIN_SCORE=0.35` лежит между шумом и настоящими попаданиями с четырёхкратным запасом в обе стороны.

Третья строка показательна: вопрос **по данным** тематически близок к регламентам и порогом не отсекается. Значит выбор
между «посчитать» и «процитировать» делает агент при выборе инструмента, а порог отвечает только за отсев постороннего.
Описание
`search_regulations` прямо говорит, что инструмент не отвечает на вопросы про суммы.

## Корректность данных

Одни и те же деньги записаны в выгрузке дважды: детально и итогом в ОСВ. При каждой загрузке это сверяется — проверка
ловит не порчу данных, а ошибки загрузчика:

| Сверка                                                 |      Значение |
|--------------------------------------------------------|--------------:|
| Σ `invoices_issued.amount` = оборот Дт 62.01           | 59 900 852,77 |
| Σ (`amount` − `paid`) = сальдо 62.01 = Σ `receivables` | 28 064 859,21 |
| Σ `invoices_received.amount` = оборот Кт 60.01         | 24 907 870,92 |

Расхождение не роняет сервис — оно попадает в `warnings` ответа.

Два поля вычисляются при загрузке, потому что в CSV их нет:

- **`due_date`** = `date + term_days` — без него не отвечается вопрос о сроках оплаты;
- **`direction`** у платежей — в `payments.csv` лежат платежи в обе стороны (31 835 993,56 приходов и 14 787 622,76
  расходов). Направление определяется по префиксу счёта в назначении платежа; корректность разбора подтверждена тем, что
  обе суммы сошлись с оборотами 62.01 и 60.01 до копейки.

Суммы хранятся как `REAL`. Канонический ответ для денег — `Decimal` или копейки в `INTEGER`; я проверил обе схемы на
этих данных, агрегаты совпадают до копейки, поэтому для MVP оставлен `float` с обязательным округлением до двух знаков
на выходе. Для продакшена взял бы `Decimal`: совпадение на 130 строках не масштабируется.

## Безопасность и надёжность

| Требование                        | Как сделано                                                                                                                                    |
|-----------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| Секреты                           | только через env, `.env` в `.gitignore`, в репозитории `.env.example` без значения ключа                                                       |
| Данные только на чтение           | `PRAGMA query_only = ON` после загрузки; есть тест                                                                                             |
| Нет произвольного SQL             | фиксированные запросы, условия из закрытого перечня в коде, значения всегда через плейсхолдеры `?`; LLM передаёт аргументы, а не текст запроса |
| Валидация входа                   | pydantic: непустой вопрос, ≤ 500 символов, обрезка пробелов до проверки; пустой запрос → 422                                                   |
| Валидация аргументов инструментов | pydantic-модель на каждый инструмент; `Literal` для перечислений, регулярное выражение для дат                                                 |
| Лимиты                            | ≤ 4 витков, бюджет 8000 токенов, `LIMIT` в каждом запросе к данным                                                                             |
| Таймауты                          | 5 с на соединение, 60 с на ответ модели                                                                                                        |
| Ретраи                            | 1–2 попытки на 429/5xx и обрыв соединения; **на таймаут повтора нет** — модель уже занята, повтор только добавит ей работы                     |
| Ошибки инструментов               | ловятся, превращаются в `warnings`; сервис не падает и не выдумывает ответ                                                                     |
| Цитаты                            | проверяются на дословное вхождение в файл; не прошедшая проверку цитата отбрасывается                                                          |

### Про `PRAGMA query_only`

Формулировка честная: модель в этой архитектуре **вообще не порождает SQL**. Поэтому режим только чтения защищает не от
неё, а от ошибки в коде инструмента, и служит проверяемым доказательством, что данные не меняются. Защитой от инъекции
он не является.

## Замеры

12 прогонов на вопрос, локальная Ollama `qwen2.5:7b-instruct`, RTX 5060 8 ГБ. Модель прогрета: первый вызов после
простоя включает загрузку весов в видеопамять.

| Тип вопроса       | Медиана | Худший | Лучший | Ориентир ТЗ | Витков | Токенов вх./исх. | Доля `ok` |
|-------------------|--------:|-------:|-------:|------------:|-------:|-----------------:|----------:|
| простой расчётный |   1,0 с |  1,6 с |  0,9 с |        10 с |      2 |        3980 / 69 |      100% |
| RAG с цитатами    |   2,6 с |  3,1 с |  1,9 с |        12 с |      2 |       4469 / 172 |      100% |
| многошаговый      |   2,3 с |  2,7 с |  2,1 с |        25 с |      2 |       4102 / 169 |      100% |

Воспроизвести: `uv run python scripts/bench.py --runs 12`

**Прямая стоимость нулевая** — модель локальная. Токены считаются по-настоящему (`usage` из ответа API) и ограничены
бюджетом; для оценки облачного варианта скрипт принимает `--price-in` и `--price-out` за 1M токенов.

Где узкое место: ~1300 токенов входа на каждый вызов — это описания шести инструментов, и они отправляются на каждом
витке. Самый дешёвый способ сократить бюджет — сузить набор инструментов до релевантных до первого вызова модели.

Разовые издержки старта (в бюджет запроса не входят, выполняются в `lifespan`):

|                                     |         |
|-------------------------------------|--------:|
| Загрузка модели эмбеддингов из кеша |   8,7 с |
| Загрузка CSV в SQLite и сверка      | < 0,1 с |
| Поиск по регламентам                |   14 мс |

### Найденная и устранённая ненадёжность

На RAG-вопросе доля правильных ответов была **80%**: в двух прогонах из десяти модель отвечала текстом, не вызвав ни
одного инструмента.

`tool_choice: "required"` проблему не решил — Ollama соблюдает его не всегда. Поэтому в цикл добавлена проверка: если на
первом витке инструмент не вызван, ответ не принимается, модели отправляется требование вызвать инструмент. После этого
**20 прогонов из 20 успешны**.

Это же свойство означает, что ни один ответ не может появиться без обращения к данным или регламентам.

**Вторая находка — «Q2» как период с начала года.** На вопросе «Обороты по счёту 62 за Q2 2026» модель передавала
`date_from: 2026-01-01` вместо `2026-04-01`, то есть читала «за квартал» как «нарастающим итогом по конец квартала».
Ответ получался 55 516 925,39 вместо 21 397 501,10 — правдоподобный и неверный.

Лечится описанием аргументов: границы кварталов перечислены явно в JSON Schema инструмента. После правки 9 прогонов из 9
верны, включая формулировки «Q2 2026», «второй квартал 2026» и «Q2 2026 (Дт, выставлено)».

Вывод, который стоит зафиксировать: описания инструментов — это часть промпта, а не документация. Оба сбоя устранены
правкой описаний и одной проверкой в цикле, без усложнения архитектуры. И оба нашлись только потому, что ответы
проверялись на реальных числах, а не «на глаз».

## Что сделал бы перед продакшеном

1. **Персистентность и аудит.** Postgres для истории запросов и ответов: кто спросил, какие инструменты вызвались, какие
   числа вернулись. Без этого нельзя разобрать ни одну претензию к ответу.
2. **Evals в CI.** Набор из 15–20 вопросов с эталонными числами, прогон на каждый pull request. Промпт — это код: правка
   одной строки меняет поведение, и ловить это должен автотест, а не пользователь.
3. **Auth и RBAC.** Данные о задолженности видны не всем: менеджер должен видеть своих контрагентов, финдиректор — всех.
   Фильтр по `manager` уже есть в справочнике.
4. **Семантический кеш.** Финансисты задают одни и те же вопросы каждое утро. Кеш по эмбеддингу вопроса с инвалидацией
   по времени выгрузки данных срежет большую часть нагрузки и стоимости.
5. **Observability.** Трасса уже пишется — осталось отправлять её в OpenTelemetry и собирать дашборд: доля `not_found`,
   распределение витков, токены на запрос, латентность по типам вопросов.

Архитектура к этому готова: конфигурация вынесена в env, ресурсы собираются в одном месте (`startup.py`), инструменты не
знают про LLM, а агент не знает про CSV.

## Бизнес-сценарии, которые видны в данных

**1. Еженедельный реестр просроченной дебиторки по стадиям регламента.**
В `receivables.csv` есть `overdue_days`, в регламенте — пять стадий с диапазонами и предписанными действиями. Агент раз
в неделю раскладывает 14 позиций по стадиям и формирует для каждого менеджера список: кому звонить, кому слать
претензию, что передавать юристу. Сейчас это делается вручную. Внедряется в первый месяц:
нужен только планировщик и рассылка — вся логика уже есть.

**2. Контроль резерва по сомнительным долгам.**
Учётная политика задаёт пороги 45 и 90 дней (50% и 100% суммы). Данных достаточно, чтобы на отчётную дату посчитать
требуемый резерв и сравнить с фактически начисленным по счёту 91.02. Расхождение — это либо недоначисленный резерв, либо
ошибка в учёте, и то и другое всплывает на закрытии периода. Тоже реалистично в первый месяц: добавляется один
инструмент.

**3. Платёжный календарь и кассовые разрывы.**
`invoices_received` с вычисленным `due_date` даёт график обязательных платежей,
`invoices_issued` — ожидаемые поступления, счёт 51 — текущий остаток. Сопоставление трёх рядов показывает недели, где
расход обгоняет приход. Это уже полноценный прогноз ликвидности, и он требует данных за больший период, чем семь месяцев
выгрузки, — реалистичный срок второй-третий месяц.

Общий принцип: везде агент **готовит решение и обосновывает его ссылками**, а проводит операцию человек. Инструментов,
меняющих данные, в сервисе нет вовсе.

---

## Что не успел

- **MCP-сервер** (бонус до +5) — не начат.
- **Eval-прогон** (бонус до +5) — не начат; эталонные числа для него уже посчитаны и зафиксированы в тестах и в разделе
  «Корректность данных».
- **`draft_payment` с human approval** (бонус до +5) — не начат.
- Из реализованных бонусов: **трейсинг** (витки, вызовы инструментов, токены — в логе и по флагу `--trace`) и **разбор
  бизнес-сценариев** выше.

Отдельно: детерминированная подсказка для выбора стадии регламента по числу дней из вопроса. Сейчас стадию выбирает
модель, получая три соседних раздела, — работает надёжно (20 из 20), но эмбеддинги ранжируют «Стадию 2» и «Стадию 3»
почти одинаково (0,639 против 0,625), потому что различаются они только числами. Правило на регулярном выражении убрало
бы зависимость от модели в этом месте.
